## M3 基础审批闭环（8 人日）—— 全项目最重里程碑

- **BPMN 校验规一化门禁（核心）**：前端 bpmn-js 提交 BPMN XML → 后端解析校验（节点类型白名单、结构合法性、嵌套深度）→ **规一化**：审批 UserTask 统一改写为多实例节点 + completionCondition（D1 的落实点）→ 部署至 Flowable；`wf_workflow_definition/version`（PRD 5.5–5.6）版本快照、旧实例绑定旧版本；业务属性统一从 `extensionElements` 读写（相对 PRD 12.1 的升级已由用户拍板，PRD 修订待同步）
- `TaskAssignmentService` 审批人解析（PRD 12.2 六种来源 + 找不到人就 BLOCK 策略）
- 提交审批事务链（PRD 10.1）：Mongo 先写 → MySQL 事务（审批单+流程启动+投影+操作记录）→ 孤立数据补偿标记；幂等键 v1
- 待办/已办/我发起查询（走投影表）；同意/驳回（驳回=change-state 到申请人节点，白名单 v1）
- `wf_approval_task` 投影同步：task/activity 事件监听器
- 时间线聚合（PRD `GET /approvals/{id}/timeline`）
- 前端本轮完成 bpmn-js 流程设计器（受限 palette + 业务属性面板）→ 发布审批 → 审批列表/详情页
- 验收：PRD 18/第三阶段闭环 + "新增简单审批不改 Java 代码"

**M3 已收口（后端，`m3-complete` tag）：** BPMN 校验规一化门禁（`BpmnValidationService`）落实 D1：类型白名单（`StartEvent` 等按 `getSimpleName()` 匹配）+ 结构/深度校验 → 规一化 → `BpmnXMLConverter` 重序列化 → 部署 Flowable → `wf_workflow_definition/version` 版本快照（`bpmn_hash` SHA-256）。**规一化 collection 驱动（Flowable 6.8 实测映射，`S6CollectionProbeTest` 实证序列化→部署→运行时 assignee 全通）**：审批 UserTask 注入 `flowable:collection="wf_users_<id>"` + `flowable:elementVariable="wf_assignee_<id>"` + `assignee=${wf_assignee_<id>}`（`setInputDataItem(集合变量名)`→collection、`setElementVariable(元素变量)`→elementVariable）；自带 MI 节点不改写但校验 collection 名须节点专属（N3，拒绝 legacy loopCardinality）。**申请节点例外（N1 修正）**：起始事件直达的 UserTask 保持普通任务（`assignee=${applicantUserId}`）不注入 MI——实测 changeState 重新进入 collection-MI 节点只造空壳执行树（act_ru_task 空、inactive scope），退回申请人必须依赖普通任务形态（M0 S1 T06 实证）。`TaskAssignmentService` 六来源（USER/ROLE/DIRECT_MANAGER/DEPT_LEADER/FORM_FIELD/EXTERNAL_API）+ 找不到人 BLOCK；`ApprovalSubmissionService` 提交事务链（PRD 10.1：幂等键先行 → Mongo 先写 → MySQL 事务：审批单+流程启动+投影+操作记录 → operation SUCCESS），提交时自动完成填单节点任务（`syncTasks` 两轮查询：createTaskQuery 是快照，完成 apply 后须重查审批任务再写投影）；`ApprovalTaskService` 同意=complete→流程结束 APPROVED、驳回=change-state 到申请人节点→RETURNED（白名单 v1）+ 申请人任务重建；待办/已办走投影表、我发起、时间线聚合；`ApprovalDefinitionService` CRUD+publish（表单+流程综合校验）；REST `/workflow/approval-definitions` `/workflow/workflows` `/workflow/approvals` `/workflow/tasks`。验收 `M3ApprovalFlowAcceptanceTest` 6/6 绿（Order 0 自清理可重跑：定义发布→提交投影→同意 APPROVED→驳回 RETURNED→幂等扣重）；回归 M2 3/3 + M1 2/2 绿。踩坑记录：白名单大小写（`StartEvent` 非 `startEvent`）；Flowable 6.8 `MultiInstanceLoopCharacteristics` 无 `getLoopDataInputRef`（编译报错）；`BpmnValidationService` 需 `@Service`（No qualifying bean）；`createTaskQuery().list()` 为快照须两轮查询。

# 六、工程规范与流程

1. **目录：** 后端 `workflow-server/`，前端 `workflow-web/`（现有空目录启用）；
2. **分支：** `main` 保护（PR 校验后合并）；每里程碑 `feature/m1-...` 分支；提交信息 `docs:/feat:/fix:/test:` 前缀；
3. **数据库：** 一律 Flyway 新版本脚本，禁止手改已发布脚本；
4. **测试：** 引擎相关能力必须有集成测试（M0 模式延伸到业务层）；每里程碑结束跑全量测试 + 推 GitHub；
5. **AI 结对章程：** AI 写每个符号前后按 GitNexus 规程做 impact/detect_changes 管理；实测优先于文档断言——任何与《可行性分析》矛盾的引擎行为立即更新分析文档并在 commit message 注明。

# 八、附录：Redis 用途设计（按需可选，接口先行）

**设计原则三条红线：**

1. 流程状态、待办事实、权限判定的**事实源永远是 Flowable/MySQL**（PRD 7.1"引擎是事实源"的镜像原则）；Redis 挂掉只降体验、不影响正确性；
2. MySQL↔MongoDB/Flowable 的跨库一致性协调**不靠 Redis**（已有 Outbox + 幂等表 + 补偿方案）；
3. 全部能力必须可**自动降级**：锁→数据库行锁兜底；防抖→MySQL 幂等表兜底；缓存→直接回源数据库。

**用途清单（接口定义在 `approval-common`，默认实现无 Redis，Redis 实现为可选装配）：**

| # | 用途 | 说明 | 结构 | 引入时机 |
|---|------|------|------|---------|
| R1 | 登录防爆破 | 同一 username/IP 错误计数 + 锁定 | `INCR+EXPIRE` | M1 可加 |
| R2 | JWT 立即失效 | 登出/改密/停用账号写黑名单，TTL=剩余有效期（PRD 4.1"停用即失效"的硬保障） | `SET+TTL` denylist | M5 必启用 |
| R3 | 审批操作互斥锁 | 同 `processInstanceId` 并发操作串行化（双击同意、转交竞态） | Redisson 锁 | M4/M5 |
| R4 | 组织结构缓存 | 审批人解析高频读部门树/主管链/角色 | cache+变更失效 | M3 可加 |
| R5 | 幂等短窗防抖 | 高频重复提交防抖，**MySQL 幂等表仍是最终防线** | `SETNX+TTL` | M5 |
| R6 | 待办超时提醒 | 延迟队列（扩展项，PRD 暂无 SLA 需求） | `ZSET` | P3 扩展 |
| R7 | 定义热缓存 | `wf_workflow_version.config_json` 读多写少 | cache+发布失效 | P3 扩展 |

**M5 前必须启用的最小集：R1、R2、R3、R5。**
